# Proposal: Build and Publish `.deb` Files via GitHub Actions and GitHub Releases

**Date:** 2026-08-22
**Related:** [14-debian-ubuntu-packaging.md](14-debian-ubuntu-packaging.md), which surveys the full
archive-packaging landscape (Debian archive via DHG, Ubuntu PPA, static-binary `.deb`) and whose
`debian/` output this proposal builds on. That document's Track C ("static-binary `.deb`") flags
GitHub Releases as "a reasonable complement... attached to GitHub Releases today," but Track C is
specifically a toolchain-free, statically-linked binary via `fpm`/`checkinstall` — not what this
document recommends. This document proposes a new, distinct **Track D**: build the *real*,
distro-integrated `debian/` directory (Track A/B's output) on a GitHub-hosted runner and publish
the result via GitHub Releases instead of an archive or PPA.

**Decision:** Reuse the real `debian/` packaging already merged into `main` (Track A/B's output),
building it on GitHub-hosted Ubuntu runners with `apt`-installed Haskell packaging tools, rather
than hand-rolling a second, parallel packaging path with `fpm`/`dpkg-deb`.

---

## Problem

`ai-planning/14` lays out how to get `setdown` into the Debian archive (Track A) and an Ubuntu PPA
(Track B) — both real, valuable, but slow: DHG sponsorship and archive transitions take "weeks to
a few months", and a PPA needs a Launchpad account, GPG key, and per-series re-uploads. Neither
gets a user a `.deb` *today*.

Meanwhile `debian/` already exists in this repo (merged via PR #8), generated by `cabal-debian`
against `setdown.cabal`. It has never actually been built — not in CI, and not verified locally in
this session either (this proposal was written on macOS, where `dpkg-buildpackage` doesn't run).
Whether it builds cleanly is exactly what the spike work item below needs to confirm; the gap this
proposal addresses is **automation and distribution** once it does: there is no CI job that builds
`debian/`, and no place a user can download the result from. GitHub Releases already exists as a
distribution point for every tagged version of this repo — it just has no `.deb` attached to it.

This proposal covers: what a GitHub Actions workflow needs to build `debian/` into a `.deb` on a
GitHub-hosted runner, and how to attach that `.deb` to a GitHub Release automatically.

---

## Two ways to produce the `.deb` in CI

### Approach A — build the real `debian/` directory (recommended)

Install the same tools DHG/a Debian builder would use, on a GitHub-hosted Ubuntu runner, and run
`dpkg-buildpackage` against the `debian/` directory that already lives in this repo:

```shell
sudo apt-get install -y debhelper haskell-devscripts-minimal cdbs ghc devscripts lintian \
  libghc-async-dev libghc-split-dev libghc-uuid-dev libghc-cmdargs-dev \
  libghc-quickcheck2-dev libghc-tasty-dev libghc-tasty-golden-dev \
  libghc-tasty-hunit-dev libghc-tasty-quickcheck-dev
dpkg-buildpackage -us -uc -b
```

Verified before writing this proposal: GitHub's `ubuntu-24.04` runner image is Ubuntu noble, and
noble's `universe` component carries `haskell-devscripts` (0.16.33ubuntu1), `cdbs`, and
`libghc-async-dev` — the same packages `debian/control` already declares as build-dependencies.
The rest of the `libghc-*-dev` list in `debian/control` are ordinary DHG-synced packages of the
same shape, so the same should hold; the "Verify" work item below confirms every entry, not just
the three spot-checked here.

**Why this is the better default:**
- Zero duplicate packaging logic. `debian/control`'s dependency list, `debian/copyright`,
  `debian/rules`' build steps — all of it is exercised exactly as a real Debian/Ubuntu build would
  exercise it. There's only one packaging path to keep correct, not two.
- It's a free regression check for Track A. The DHG archive-submission process (ITP, sponsor
  review) won't be attempted for a while yet; a CI job that runs `dpkg-buildpackage` + `lintian` on
  every release catches packaging breakage (a bumped dependency bound, a renamed module, a stale
  `debian/copyright` entry) months before a human sponsor would.
- `${haskell:Depends}`/`${shlibs:Depends}` (populated by `haskell-devscripts`/`dpkg-shlibdeps`)
  give a *correct*, automatically-derived `Depends:` line for the actual shared libraries the
  binary links against — not a hand-maintained guess.

**A real blocker to resolve first: the test suite shells out to `stack`.** `debian/rules` sets
`DEB_ENABLE_TESTS = yes`, so `dpkg-buildpackage` will run all three test suites as part of the
build. `test/GoldenTests.hs` (both `goldenTest` and `errorTest`) invokes the binary under test via
`callProcess "stack" ["exec", "--", "setdown", ...]` — not the binary `cdbs` just built. A cdbs/
`haskell-devscripts` build environment has no `stack` installed and no `stack.yaml` resolver
available, so these suites will fail to even launch, not just fail their assertions. This needs a
fix — most likely, teaching `GoldenTests.hs` to invoke the freshly-built binary directly (e.g. via
a path passed through an environment variable or discovered relative to the test binary) instead
of shelling out to `stack` — before Approach A can work at all, independent of anything in this
workflow. Cheap to fix now; the spike work item below will discover it the hard way otherwise.

**The one wrinkle: `debian/changelog`.** Its current top entry is
`haskell-setdown (0.2.0.0-1) UNRELEASED; urgency=low` — deliberately unreleased, because Track A's
real archive upload needs to control that entry (e.g. rewriting `urgency`/`distribution` and
closing the ITP bug at actual upload time). The CI build must **not** commit changes to this file.
Instead, the workflow should stamp a throwaway version into a **scratch copy** of the changelog at
build time, derived from the pushed release tag:

```shell
dch --changelog debian/changelog --newversion "${PKG_VERSION}-1" --distribution UNRELEASED \
  --force-distribution "CI build for ${GITHUB_REF_NAME}"
```
run in the checked-out working copy inside the job (which is discarded when the job ends), never
committed back to the branch.

### Approach B — self-contained build via `stack` + `dpkg-deb` (fallback)

Build the executable the same way the existing `test.yml` workflow already does (`stack build`),
then hand-assemble a minimal package: `usr/bin/setdown` plus a small `DEBIAN/control` stanza, built
with `dpkg-deb --build` (present on every Ubuntu runner, no extra install). `Depends:` would need
to be derived by hand from `ldd $(stack path --local-install-root)/bin/setdown` (expect `libc6`,
`libgmp10`, `libffi8` or similar) rather than computed automatically.

This avoids depending on Ubuntu's `libghc-*-dev` package set matching `setdown.cabal`'s bounds at
all, which is a real (if currently-verified-fine) coupling in Approach A. But it's a second
packaging mechanism running in parallel with the one Track A will eventually submit to Debian,
built with a different toolchain (Stack's GHC/resolver, not Debian's), so the two could drift and
disagree about correctness — e.g. Approach B could keep "working" in CI after a change that would
actually break the real Debian package.

**Recommendation: use Approach A.** Keep Approach B in reserve — if Approach A turns out to be
too fragile or slow in practice (see spike work item below), fall back to it rather than starting
there.

## Workflow design

New file: `.github/workflows/release-deb.yml`.

- **Trigger:** `on: push: tags: ['v*']`. A pushed tag is the signal that a version is ready to
  ship; this mirrors how most projects gate release automation, and keeps it decoupled from the
  existing `test.yml`, which runs on every push/PR and should stay fast.
- **Version/tag consistency check:** first step parses the tag (`v0.2.0.0` → `0.2.0.0`) and fails
  the job if it doesn't match the `version:` field in `setdown.cabal`. This stops a mistagged
  release from shipping a `.deb` whose version lies about what code it contains.
- **Matrix:** `{ubuntu-24.04, ubuntu-24.04-arm}` → `amd64` and `arm64` `.deb`s. `ubuntu-24.04-arm`
  is a free GitHub-hosted runner for public repositories (this repo is public), so no
  QEMU-emulated cross-build is needed for arm64 — it's a native build on each architecture.
- **Per-job steps:** checkout → `apt-get install` the packaging toolchain (list above) → stamp the
  scratch changelog entry (Approach A wrinkle, above) → `dpkg-buildpackage -us -uc -b` → `lintian
  ../*.deb` (treat `error`-severity tags as build failures; warnings are fine, `debian/` will
  accumulate suppressions over time as Track A matures it) → move the produced `.deb`
  (`dpkg-buildpackage` places it one directory above the source tree) to a predictable path.
- **Publish:** attach the `.deb` from each matrix leg to the GitHub Release for that tag —
  `gh release upload "$GITHUB_REF_NAME" setdown_*.deb` (using the Actions-provided `GITHUB_TOKEN`,
  `permissions: contents: write`) is enough; no third-party action needed; if the release itself
  doesn't exist yet for this tag, `gh release create "$GITHUB_REF_NAME" --generate-notes` first.
- **Artifact naming:** `dpkg-buildpackage` derives it from `debian/control` automatically —
  `setdown_<version>-1_amd64.deb` / `setdown_<version>-1_arm64.deb`.

## What changes in the README

Once this ships, add to the Installation section:

```shell
curl -LO https://github.com/robertmassaioli/setdown/releases/latest/download/setdown_<version>-1_amd64.deb
sudo dpkg -i setdown_<version>-1_amd64.deb
sudo apt-get install -f   # pulls in the plain C runtime libs (libc6, libgmp10, libffi8, …) if dpkg -i complains
```

GHC statically links the Haskell libraries a program depends on into its executable, so the
package's `Depends:` (computed automatically by `${shlibs:Depends}`) is ordinary C shared
libraries, not `libghc-*` packages — confirmed by checking Debian's real `shellcheck` package
(`14`'s closest precedent for an executable-only Haskell `.deb`), whose `Depends:` is `libc6`,
`libffi8`, `libgmp10`, `libnuma1`. No `libghc-*` runtime dependency exists to pull in.

Worth being explicit in that README section that this is **not** an `apt`-managed install: no
signed repo, no `apt install setdown`, no automatic upgrades — just a downloadable artifact. That
distinction is why Tracks A and B in `14` remain worth pursuing independently; this track is
strictly faster to ship and lower-leverage per install, not a replacement.

## Concrete work items

| Item | Notes |
|---|---|
| Fix `test/GoldenTests.hs` to invoke the built binary directly instead of `callProcess "stack" [...]` | Blocks Approach A outright under `DEB_ENABLE_TESTS = yes`, since no `stack` exists in a cdbs build environment — see above |
| Spike: run Approach A's `apt-get install` + `dpkg-buildpackage` list end-to-end on an `ubuntu-24.04` GitHub runner (`workflow_dispatch`-only, no publish step) | Confirms every `libghc-*-dev` entry resolves, not just the three spot-checked above, and that `debian/` as committed actually builds — it has never been built anywhere, in CI or otherwise |
| Add tag/`setdown.cabal` version consistency check | Fail fast on a mistagged release |
| Write `.github/workflows/release-deb.yml` (Approach A, matrix over amd64/arm64) | Scratch-changelog stamp, `dpkg-buildpackage`, `lintian`, upload to the release |
| Decide `lintian` failure policy | Which tags/severities block the build vs. just warn; `debian/compat` (currently `10`) is a deprecated mechanism modern packaging replaces with `debhelper-compat (= N)` in `Build-Depends`, so expect at least one pre-existing tag on `debian/` as committed, independent of anything this workflow does |
| Update README installation section | `curl` + `dpkg -i` instructions, once a release has a `.deb` attached |
| (Optional) lightweight "packaging still builds" smoke job in `test.yml` on every push/PR | Build-only, no `lintian`/no publish — earlier warning than waiting for a release tag; adds apt-install time to every CI run, so weigh against `test.yml` staying fast |

## Open questions

- Should the arm64 leg block the release if it fails, or should amd64-only ship and arm64 be
  best-effort while the packaging is new? Recommend **block** — a partially-published release
  (amd64 present, arm64 silently missing) is a worse failure mode than a slower release.
- `ubuntu-24.04` will eventually be superseded as GitHub's default runner label; when it is, the
  `libghc-*-dev` version set this workflow depends on moves too. No action needed now, but this
  workflow will need periodic revisiting the same way `stack.yaml`'s resolver already does.
- Does Track A's eventual real Debian upload want to *reuse* this workflow's `lintian` output as a
  pre-submission check, or keep them fully separate? Leaning toward "this workflow's success is a
  useful signal, not a formal gate" — no coupling needed, just noting the overlap.
